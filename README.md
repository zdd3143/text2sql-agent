# 自然语言查数据库（Text-to-SQL Agent）

> 从零手写的 Text-to-SQL Agent。**不依赖 LangChain / LangGraph**，
> 自己实现 ReAct 循环、工具调用与 SQL 执行反馈。
> 重点是**失败归因**与**评估驱动的优化**。

## 30 秒看懂

| 项 | 结果 |
|---|---|
| 数据库 | SQLite，3 张表 / 24 行（公司 / 财务 / 产量），含外键关联 |
| 核心链路 | 问题 → **ReAct 循环**（思考 → 行动 → 观察）→ 生成 SQL → 执行 → 纠错 → 自然语言回答 |
| **Agent 的本质** | **模型（决策）+ 工具（行动）+ 循环（多步）** |
| 评估集 | **15 题 6 类**（简单 / 单位 / 聚合 / JOIN / 多步 / 不可答），每题带人工编写的标准 SQL |
| **宽松执行准确率** | **0.87**（范围 0.85 ~ 0.92，3 次运行）|
| 严格执行准确率 | 0.28（学术口径：结果集完全一致）|
| 有效 SQL 率 | **1.00** —— 生成的 SQL 全都能跑通 |
| 拒答准确率 | **1.00** —— 问了数据库里没有的数据，两次都老实拒答 |
| 平均步数 | 5.76 步 / 4.76 次工具调用 |

**六个核心发现**（详见「实验与发现」）

1. 干净的小 schema 上，**一次生成 SQL 就能答对 4/5** —— Agent 的价值不在这种场景
2. ⭐ **模型会编造解释来包装错误答案**：同一个字段，它先说「亿元」后说「万元」
3. **最危险的失败不是语法错，是语义错**：有效 SQL 率 100%，但准确率不是 100%
4. ⭐⭐ **评估指标本身会骗人**：我的尺子出过三次错，每次都差点得出错误结论
5. **Agent 知道自己不知道，却没有工具去查证** —— 工具的信息密度决定它的上限
6. **Agent 会把该由数据库做的计算留给自己**（口算）

## 这是什么

用户用中文提问，系统自己决定查哪些表、写 SQL、执行、发现错误后自己改，
最后用自然语言回答。

```
问题："原油产量最高的那家公司，2023年的净利润是多少？"
  ↓
[ReAct 循环]
  Thought:  先看看有哪些表
  Action:   list_tables
  Observation: companies, financials, production
  Thought:  需要看 production 的字段
  Action:   describe_table
  Action Input: production
  Observation: id, company_id, year, product, amount, unit
  Thought:  查原油产量最高的公司
  Action:   run_sql
  Action Input: SELECT company_id, amount FROM production
                WHERE product='原油' ORDER BY amount DESC LIMIT 1
  Observation: [[1, 9.36, "亿桶"]]
  Thought:  是 company_id=1，再查它的净利润
  Action:   run_sql
  Action Input: SELECT c.name, f.net_profit FROM companies c
                JOIN financials f ON f.company_id=c.company_id
                WHERE c.company_id=1 AND f.year=2023
  Observation: [["中国石油", 1611.5]]
  Final Answer: 原油产量最高的公司是中国石油（9.36亿桶），
                其2023年净利润为1611.5亿元。
```

**注意它分了两步查**，而不是硬写一条大 SQL —— 这正是 Agent 的价值：
**可以把问题拆成几步，每步基于上一步的真实结果决定下一步。**

## 为什么不用 LangChain / LangGraph

整套机制一共 100 行左右：一个 `for` 循环 + 一张工具分发表。
自己写一遍才知道框架到底替你做了什么。

**具体收获**：

- **"工具调用"的本质是：模型只负责"决定调哪个"，真正执行的是你的代码。**
  模型自己什么都做不了，它只会输出文字。
- **`messages` 数组为什么会越来越长**：模型的思考（`assistant`）和工具的反馈（`user`）
  都被追加进对话历史 —— 这就是 Agent 的"记忆"，也是它上下文会爆的原因。
- **工具返回什么信息，直接决定模型能不能纠错**（见发现 ⑤）。

## 实验与发现

### ① 干净的小 schema 上，"一次生成"就够了

**做法**：把 3 张表的完整 schema 塞进提示词，让模型一次生成 SQL，执行，**不循环**。

**结果**：5 个问题**答对 4 个**，包括一道需要**自连接**的题。

**结论**：**Agent 的价值不在"干净的小库"上。**

这个 schema 只有 3 张表、字段名直白（`revenue` / `net_profit`）、数据干净。
真正的企业库是：表名像 `T_FIN_2023Q4_BAK`，字段是 `A0101`、`yysr` 这种代号，
同一个"营业收入"在三张表里口径不同。**那才是 Agent 的主场。**

### ② ⭐ 模型会编造解释来包装错误答案

同一个字段 `revenue`，它在两道题里给出了**两个不同的单位**：

| 题 | 回答里的"说明" | 实际用的阈值 |
|---|---|---|
| q005 超过 1 **万亿** | "revenue 字段的单位为【**亿元**】，1 万亿元 = 10000 亿元" | `revenue > 10000` |
| q006 超过 1 **亿** | "revenue 字段单位为【**万元**】，超过1亿元即 revenue > 10000 万元" | `revenue > 10000` |

**它两次用了同一个阈值，只是倒推了两个不同的单位来解释。**

q005 恰好蒙对了，q006 错了（正确答案 6 家，它说 2 家）。

**而且它的措辞在反复横跳**：

- q001："（单位与表中一致）"
- q003："（单位以数据库原始记录为准，**通常为亿元**）"
- q005："（单位**为亿元**）" ← 开始用肯定语气了
- q006："（单位**为万元**）" ← 换了一个，同样是肯定语气

> **这比"答错"危险得多。**
>
> 单纯的错误，用户会怀疑；但**错数字配上看起来很专业的"字段说明"**，
> 大多数人就信了 —— **错误被包装成了可信**。
>
> 这是"引用幻觉"的变体：RAG 项目里是**假答案配真格式的引用**，
> 这里是**错数字配编造的字段说明**。

### ③ 最危险的失败不是语法错，而是语义错

```
有效 SQL 率   1.0000    ← 生成的 SQL 全都能跑通
宽松准确率    0.8718    ← 但只有 87% 的答案是对的
```

**"SQL 能执行"和"答案正确"是两回事。**

单位错误那类问题尤其危险：

| | 语法错（字段名写错） | **语义错（单位理解错）** |
|---|---|---|
| SQL 能执行吗 | ❌ 报错 | ✅ **正常执行** |
| 有异常吗 | ✅ 有 | ❌ **没有** |
| 返回什么 | 错误信息 | **一个看起来正常的结果** |
| 你能发现吗 | 一眼发现 | **得自己算一遍才知道** |

> **崩溃你知道要修；返回一个正常但错误的数字，你还以为它答对了。**

### ④ ⭐⭐ 评估指标本身会骗人

**我的尺子出过三次错，每一次都差点让我得出错误结论。**

| # | 现象 | 真因 |
|---|---|---|
| 1 | 执行准确率只有 **46.7%** | **判定标准太严**——它把"多查了一列"当成错误。用户问"营收最高的公司是哪家"，Agent 返回 `('中国石化', 32122.2)`，多带了数值，其实答得更好 |
| 2 | 同一份代码跑两次，13 题里 **4 题行为不同** | 一开始归因于 **LLM 非确定性**（`temperature=0` 也不保证确定）|
| 3 | q012 判"没有产出可执行的 SQL"、q010 判"✅" | **两个真 bug**：① trace 里 `arg[:200]` 把长 SQL **截断了**，评估重新执行时变成语法错；② 宽松判定放过了"查到过但没答出来"（回答是"达到最大步数，未得出结论"）|

**修完之后的对比**：

| 指标 | 修之前 | 修之后 |
|---|---|---|
| 严格准确率 | 0.1538 | 0.2821（范围 0.23~0.31）|
| 宽松准确率 | 0.7692 | **0.8718（范围 0.85~0.92）** |
| 噪声幅度 | 估计 ±20pp | **实际 ±4pp（约 1 道题）** |

> **第 2 条尤其值得说**：我原以为"两次结果不同"是模型不确定性的锅，
> 修完两个 bug 才发现 —— **一部分"随机性"其实是评估 bug 造成的假象。**
>
> **把测量工具的缺陷误判成被测量对象的特性，是很容易犯的错误。**

**教训**：

> **指标异常时，先怀疑指标，再怀疑模型。**

这是我在两个项目里第二次踩同一个坑：

| 项目 | 表面现象 | 真因 |
|---|---|---|
| RAG 项目 | 重排把正确答案从第 1 打到第 7 | **我的标准答案定义太窄** |
| 本项目 | 执行准确率只有 46.7% | **我的尺子太严** |

### ⑤ Agent 知道自己不知道，却没有工具去查证

引入 ReAct 循环后，看它回答的结尾措辞：

```
"营业收入为 32122.2（单位与表中一致）"
"净利润为 1611.5（单位与表中一致，通常为亿元）"     ← 它在猜
```

**它多次主动声明"不知道单位"**，还补了"通常为亿元"——
**它在猜，而且知道自己是在猜。**

**但它的工具给不了答案**：

```
describe_table(financials) →
  revenue REAL        ← 只有字段名和类型，没有单位、没有口径、没有样例数据
  net_profit REAL
```

更关键的是：**它从头到尾没有运行过 `SELECT * FROM financials LIMIT 3`**——
**它从来没"看过"数据长什么样**，只知道字段叫 `revenue`，
不知道这个数是 `32122` 还是 `32122000000`。

> **两个结论**：
> 1. **加循环修不了单位问题** —— SQL 执行成功、没有报错，
>    循环里没有任何信息告诉它单位错了。它需要的是**更好的上下文**，不是更多的尝试机会。
> 2. **工具的信息密度，决定 Agent 的能力上限。**

### ⑥ Agent 会把该由数据库做的计算留给自己

q011「中国石化和中国石油2023年的营业收入**相差多少**？」：

```
Agent 的 SQL:  SELECT c.name, f.revenue FROM ... WHERE c.name IN (...)   ← 只查了两个原始值
最终回答:      "两者相差约 2012.1"                                        ← 它自己心算的
```

**它算对了**（32122.2 − 30110.1 = 2012.1）。但注意它的措辞：**"约 2012.1"**——
**它自己也不确定算得对不对，所以加了"约"。**

**这违反了 Text-to-SQL 的设计原则**：

> **Text-to-SQL 存在的全部理由，就是把计算交给数据库。**
> 如果让模型在自然语言层做算术，那直接给它两个数字让它口算就行了，不需要 SQL。

**三个具体问题**：

| 问题 | 说明 |
|---|---|
| **它会算错** | 大模型算术不可靠，尤其大数、多步 |
| **没有校验** | SQL 的计算有数据库保证；口算错了没人知道 |
| **不可审计** | SQL 是白纸黑字的证据；"它在脑子里减了一下"没法追溯 |

**评估判定它 ❌ 是正确的** —— 它抓住的是"设计原则被违反"，不是"格式不好看"。

### ⑦ 每次都要重新探索 schema，完全重复

**平均 5.76 步里，约一半浪费在 `list_tables` + `describe_table` 上**，
而 schema 是静态的，每次探索结果一模一样。

→ 应该把 schema 直接放进系统提示。
**但一旦 schema 大到放不下，就变成了更难的问题**（见「下一步」）。

## 评估结果

**评估集**：15 题 6 类，每题带人工编写的标准 SQL。
**指标**：执行准确率（Execution Accuracy）—— 沿用 Spider / BIRD 等学术基准的做法。

运行 3 次取平均（`python src/stage3_eval.py --repeat 3`）：

| 指标 | 平均值 | 范围 | 说明 |
|---|---|---|---|
| **宽松执行准确率** | **0.8718** | 0.8462 ~ 0.9231 | gold 的值都在 Agent 结果里（**用户视角**）|
| 严格执行准确率 | 0.2821 | 0.2308 ~ 0.3077 | 结果集完全一致（**学术口径**）|
| 有效 SQL 率 | 1.0000 | — | 生成的 SQL 能跑通 |
| 拒答准确率 | 1.0000 | — | 不可答的问题被拒答 |
| 平均步数 | 5.76 | 5.67 ~ 5.80 | |
| 平均工具调用 | 4.76 | 4.67 ~ 4.80 | |

**按问题类型（宽松）**：

| 类型 | 准确率 | 说明 |
|---|---|---|
| simple | 1.00 (4/4) | |
| aggregate | 1.00 (2/2) | |
| multi_step | 1.00 (2/2) | |
| unanswerable | 1.00 (2/2) | 拒答 |
| join | 0.67 (2/3) | 错在 q011（口算）|
| **unit** | **0.50 (1/2)** | **错在 q006（单位）** |

**两个稳定的失败点**：

```
❌ q006 [unit] 2023年营业收入超过1亿元的公司有几家？
     期望 6 家 / 实际 2 家   （编造了"单位为万元"的解释）
❌ q011 [join] 中国石化和中国石油2023年的营业收入相差多少？
     期望 2012.1 / 实际 两行原始值（它自己心算了）
```

> **注意噪声只有 ±4pp（约 1 道题）** —— 这个精度足够用来判断"阶段 4 的工具改进有没有用"。

## 关键设计决策

| 决策 | 理由 |
|---|---|
| **手写 ReAct 而不用 LangGraph** | 机制一共 100 行；自己写才知道框架替你做了什么 |
| **工具统一接收一个字符串参数** | 分发表统一用 `TOOLS[name](arg)` 调用，不用为每个工具写特例 |
| **数据库报错原样返回给模型** | 模型看到 `no such column: xxx` 才知道怎么改；吞掉错误它就失去纠错依据 |
| **只允许 SELECT，且禁用危险关键字** | 企业场景的硬要求。两层检查防 CTE 绕过 |
| **工具返回结果截断到 20 行** | 防止 Result 太长把上下文撑爆 |
| **`max_steps = 8`** | 循环必须有上限，否则会失控烧 token |
| **`temperature = 0`** | SQL 生成要确定性 |
| **评估用标准 SQL 而不是标准答案字符串** | 自然语言答案难比对；SQL 的**执行结果**可以精确比对 |
| **同时报严格 / 宽松两个准确率** | 只报一个都会误导——严格低估"多带信息"的回答，宽松会放过"碰巧包含" |
| **跑 3 次取平均并报范围** | LLM 输出有非确定性；单次结果无法区分改进和噪声 |
| **`trace` 里的 `arg` 不截断** | 它会被评估**重新执行**；截断就改变了 SQL 的语义 |
| **评估脚本要有"完成度检查"** | 否则"查到过但没答出来"会被宽松判定误判成成功 |

## 已知局限

- 数据库只有 **3 张表 / 24 行**，远小于真实企业库
- **数据里没有单位信息**（`revenue` 是亿元但没有标注），已导致静默错误
- **评估集只有 15 题**，单题权重 6.7%；噪声约 ±4pp
- **"拒答"靠关键词判断**，本身就不可靠（更严格要引入 LLM 裁判，但又引入新不确定性）
- 每次问答都重复探索 schema，**平均 5.76 步里约一半是浪费**
- **没有处理歧义问题**（"去年"是哪一年？"营收"是合并口径还是母公司口径？）
- 没有多轮对话能力（每次都是独立问题）
- 严格准确率（0.28）远低于宽松（0.87）—— 说明 Agent **习惯多查列**，
  这在学术口径下会被判错
